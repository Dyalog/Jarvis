Server-Sent Events (SSE) let a `Jarvis` service push a stream of events to a client over an ordinary HTTP connection. The browser's [`EventSource`](https://developer.mozilla.org/docs/Web/API/EventSource) API reads the stream. SSE works in both JSON and REST modes. By default no SSE endpoints are defined, and `Jarvis` behaves exactly as it does without SSE support.

See [Server-Sent Events](./sse.md) for more information about using SSE with `Jarvis`.

### `SSEEndpoints`
|--|--|
|Description|`SSEEndpoints` names the endpoints that serve event streams. It can be either:<ul><li>a character vector of one or more endpoint names separated by commas and/or spaces</li><li>a vector of character vectors, one endpoint name per element. In a JSON configuration file, this is an array of strings.</li></ul>Names may be written with or without a leading `/`. A `/` within a name is treated as `.`, so `'/a/b'` and `'a.b'` both name the endpoint `/a/b`, handled by the function `a.b` in [`CodeLocation`](./settings-operational.md#codelocation). Empty and duplicate names are ignored.<br>Each SSE endpoint may have a function of the same name in `CodeLocation`, but doesn't need one. If there is one, it must be a monadic or ambivalent function, and may return a result or not. `Jarvis` calls it once for each client after the stream has started. See [The endpoint function](./sse.md#the-endpoint-function).|
|Default|`''` - no SSE endpoints|
|Examples|`j.SSEEndpoints←'events'`<br>`j.SSEEndpoints←'/events, /alerts'`<br>`j.SSEEndpoints←'events' 'alerts/high'`<br>In a JSON configuration file:<br>`"SSEEndpoints": "events, alerts"`<br>`"SSEEndpoints": ["events", "alerts/high"]`|
|Notes|<ul><li>`SSEEndpoints` is read when `Jarvis` starts, so changes take effect at the next `Start`.</li><li>An SSE endpoint can't also be called as an ordinary JSON or REST endpoint. Every request for an SSE endpoint's path is handled as an SSE request, and a method other than `GET` gets 405 (Method Not Allowed).</li><li>If `CodeLocation` contains something with an SSE endpoint's name that isn't a monadic or ambivalent function (for example a variable, a namespace or a dyadic function), `Start` fails with a message saying so.</li></ul>|

### `SSEHeartbeatInterval`
|--|--|
|Description|`SSEHeartbeatInterval` is the number of seconds between "heartbeats" that `Jarvis` sends on every open SSE stream. A heartbeat is an SSE comment (a line containing only `:`), which the browser doesn't pass to the page. Heartbeats do two jobs:<ul><li>They keep proxies and load balancers from closing a stream that's been idle for a while.</li><li>They detect clients that have gone away. If a heartbeat can't be sent, `Jarvis` closes that connection.</li></ul>Valid values are:<ul><li>`0` - don't send heartbeats</li><li>a positive number - the number of seconds between heartbeats</li></ul>|
|Default|`30`|
|Examples|`j.SSEHeartbeatInterval←15 ⍝ every 15 seconds`<br>`j.SSEHeartbeatInterval←0  ⍝ no heartbeats`|
|Notes|<ul><li>The heartbeat runs in its own thread, which starts only when `SSEHeartbeatInterval` is positive and `SSEEndpoints` isn't empty. The thread ends when the server stops.</li><li>`SSEHeartbeatInterval` is read when the server starts, so changes take effect at the next `Start`.</li><li>Many proxies close connections that are idle for 60 seconds or more. If your service sits behind one, keep the interval well below its idle timeout.</li><li>[`ConnectionTimeout`](./settings-operational.md#connectiontimeout) doesn't apply to SSE streams: an open stream is never closed for being idle.</li></ul>|
